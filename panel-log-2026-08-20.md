# Panel session log - 2026-08-20

Installing the Sunset page took four attempts and turned up three things about
this panel that matter more than the page does.

**Final state: `nowplaying`, `moon`, `nightkeeper`, `sunset`. `ocean` shelved.**
VM heap 67,091 of 98,304 (68%), all four report `error: null` across a cold
boot, and `sunset` fetches successfully within seconds of boot.

`moon` was dropped mid-session to make room for `sunset`, then rewritten (see
§5) and brought back; `ocean` came off instead. Only one of the two decorative
scenes fits alongside `sunset` - all three reach 93%, which does not load.
`ocean` is preserved byte-exact (sha256 `938064bcff39fe29…`, 9,605 bytes) in
the session backup and can be restored with a single PUT.

## 1. Uptime fragments the heap until the panel cannot even be backed up

Before the first reboot the panel had 9.6 days of uptime and its largest
contiguous free block was collapsing while being watched:

```
18,420 -> 17,396 -> 14,324 bytes   (free heap 36,184 -> 32,352)
```

At that point the API refused large bodies in *both* directions.
`GET /apps/script/{name}` returned **0 bytes** for `nowplaying`, `ocean` and
`moon` - a backup would have silently written empty files. A reboot restored
the largest block to 34,804.

**Reboot before any install or backup session.** A long-uptime panel silently
cannot be backed up, which is the worst possible moment to find out.

## 2. Compiling needs a large contiguous block, so upload minified

The panel is specific about this once there is room to answer at all:

```
heap too fragmented to compile
(largest contiguous block 10740 bytes, source is 11125); remove a script or reboot
```

Roughly `2 x source + ~6 KB` of contiguous heap is needed, because the upload
buffer and the compiler are live at the same time. An 11,125-byte source failed
where the same program at 8,149 bytes succeeded.

`minify_ax.py` strips whole comment lines, indentation and blank lines while
preserving `# @name` metadata, which the firmware parses. Readable source lives
in the repo; the stripped copy goes to the panel. `moon` was already minified
on-device for the same reason - this just makes the step reproducible.

```bash
python weather/minify_ax.py weather/sunset.ax -o build/sunset.min.ax
```

**Install immediately after a reboot**, before other requests fragment things.
The same PUT failed and then succeeded purely on that timing.

## 3. HTTPS does not fit alongside a full script set

With five scripts loaded, the fetch never happened:

```
14:00:24 script http: heap too tight for TLS (22944 free)
```

The script compiled, instantiated and ran; only the TLS handshake could not
allocate. Open-Meteo serves this endpoint over plain HTTP with no redirect, and
it is a public, unauthenticated, read-only forecast with no credential or
personal data in the request, so `sunset.ax` uses `http://` deliberately.

**Any future fetching script on this panel has the same constraint.** Check for
that log line before assuming a feed is simply broken.

## 4. `moon` had a latent boot-order crash - fixed, then removed for space

Rebooting surfaced a bug that 9.6 days of uptime had hidden:

```
type_error: value 'nil' does not support subscriptable
```

Root cause:

- `init()` sets `self.lh = -1` as its "no hour cached yet" sentinel and never
  assigns `self.ct`.
- `init()` calls `build_pal()` -> `update_hour_tint()`, which opens with
  `if h == self.lh return end`.
- Before NTP sync **`hour()` returns -1**, colliding with the sentinel. The
  guard fires on the first call, so `self.ct` is never assigned.
- `build_pal()` then does `self.ct[0]` on nil and throws.

Because the throw happens inside `init()`, instantiation fails permanently - it
never recovers even once time syncs.

```diff
-self.lh=-1
+self.lh=-99
+self.ct=[0x1A2038,0x203A48]
```

Verified across a cold boot before removal.

**Audit the other scripts for this shape**: a sentinel the clock can actually
return, or a field assigned only inside a conditional but read unconditionally.

### `moon` was nearly lost

When `moon` came off to make room for `sunset`, the panel held the **only**
copy of that program - it differs from `weather/moon.ax` (a different Moon) and
from `backups/2026-08-10-.../moon.ax`, which predates both the rewrite and the
fix. It was captured verbatim before deletion, which is the only reason §5's
rewrite had a starting point.

The lesson is §1's: a long-uptime panel cannot be read back. Capture scripts
*before* you need them, not when you are about to delete one.

`weather/moon-panel.ax` is now the source of truth for that program. Upload it
through `minify_ax.py`, not raw.

## 5. Moon v2 - accuracy, eclipses, and a smaller footprint

Rewritten as `weather/moon-panel.ax` v2.0 and verified on the panel.

**Phase.** v1 counted synodic months from a fixed epoch, and its epoch constant
was half a day out - a Julian Day fraction used without removing JD's noon
offset (`10962.26` should have been `10962.76`). Even corrected, the model was
weak. v2 uses the Meeus ch.48 phase angle (D, M, M' with six periodic terms).
Checked against `astropy` over two years at daily resolution:

| model | mean abs error | max abs error |
| --- | --- | --- |
| v1 | 3.64 points | **13.27 points** |
| v2 | 0.11 points | **0.43 points** |

The panel's own Bhaskara sine costs almost nothing here (0.43 vs 0.39 with an
exact sine), so it was kept. Live check at 21:28 UTC: panel showed **58%**,
astropy said **57.44%**. v1 would have shown 55%.

**Eclipses.** v1's node test **never fired once in two years**, including on
both real lunar eclipses. It compared the wrong quantity - the time of the
*new* moon against an uncalibrated draconic phase. v2 keys off the moon's
argument of latitude F, which is what actually decides eclipses: |sin F| runs
0.02-0.25 at real eclipses and above 0.39 at ordinary full moons. All four
2026-2027 lunar eclipses are now flagged, the March 2026 total flags deepest,
and the depth 0-100 drives how far the disc goes to blood red.

**Correctness.** The time fallback is gone: v1 caught a failing `epoch_ms()`
and substituted a *local time-of-day fraction* as an absolute day count, which
silently produced a nonsense phase. v2 returns nil and `should_show()` hides
the page - no clock, no honest moon. Dead fields (`prv`, `up`, `eboot`,
`edays`) removed.

**Footprint.** The 256-entry `map` list became a `bytes` buffer: same lookup,
**23,301 -> 21,647 bytes** of VM heap. Storing palette index + 1 lets 0 mean
"no pixel", since bytes cannot hold -1.

## 6. Writes into this folder are blocked by Windows, not by any tool

`git`, `python` and `bash` all fail to create files here:

```
fatal: Unable to create '.../.git/index.lock': No such file or directory
OSError: [Errno 9] Bad file descriptor
```

The directory exists and is readable; only writes fail, and they fail with a
misleading ENOENT. The cause is **Windows Controlled Folder Access**
(`Get-MpPreference` -> `EnableControlledFolderAccess : 1`), Defender's
ransomware protection. `Documents` is protected by default, and the allow-list
is per-application - the existing scheduled-task senders can write their logs,
but a freshly spawned `git.exe` or `python.exe` cannot.

Consequences: **`git commit` cannot be run from a tool here**, `pytest` cannot
write `.pytest_cache`, and any script writing output into this folder fails.
Preview renderers therefore take `--out` and were pointed at a temp directory.

To fix: Windows Security -> Virus & threat protection -> Ransomware protection
-> Allow an app through Controlled folder access, and add `git.exe` plus your
Python. Until then, commits have to be run from an already-allowed shell.

Cost depends slightly on load order, since a script loaded last pays for

**Load order also decides whether an install succeeds at all.** Installing
`sunset v3` into a running panel returned `ok:true` with
`out of memory` and `vm heap +534 bytes`: it compiled, but could not instantiate
beside four already-resident scripts. A reboot, which loads all five in order
from a clean heap, fit the same script with room to spare. **If an install
OOMs, reboot before concluding it does not fit.**

Five scripts reached 91,094 (93%) and loaded only intermittently: one boot
succeeded, the next reported `vm heap +0 bytes`. **Treat about 75% as the
practical ceiling**, not 100%.
